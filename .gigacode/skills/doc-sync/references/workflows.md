# Workflows

Пошаговые сценарии работы с doc-sync.

## Workflow: Обновление по diff

**Вход:** `git diff` или `git diff {branch}`

### Шаг 1: Анализ diff

```bash
git diff HEAD
# или для конкретной ветки
git diff main...{branch}
```

Определи:
- Какие файлы изменены (код или документация)
- Какие модули затронуты
- Характер изменений: добавление/удаление/изменение API

### Шаг 2: Определение scope

| Тип изменений | Что обновлять |
|---|---|
| Новый публичный класс | `docs/modules/{module}.md`, `docs/packages/{package}.md` |
| Новый метод в публичном API | `docs/packages/{package}.md`, `README.md` модуля |
| Новый пакет | `docs/modules/{module}.md`, создать `docs/packages/{package}.md` |
| Изменение зависимостей модуля | `docs/modules/{module}.md`, `docs/architecture.md` |
| Изменение конфигурации | `README.md` модуля |
| Изменение тестов | `docs/testing/*.md`, `docs/modules/{module}.md` |

### Шаг 3: Исследование

Запусти `Explore`-агента для каждого затронутого пакета:

```
Исследуй пакет {package-path} в модуле {module}.
Мне нужно обновить документацию после изменений в коде.
Собери:
1. Список всех публичных классов/интерфейсов/enum
2. Назначение каждого (1 предложение)
3. Ключевые методы и их назначение
4. Зависимости от других классов пакета
5. Lombok-аннотации (только если влияют на поведение)
6. Изменения в публичном API (сигнатуры, поведение)
```

### Шаг 4: Обновление

Для каждого файла:
1. Прочитай текущую версию
2. Внеси точечные изменения (add/remove/modify)
3. Обнови `last_updated`
4. Проверь кросс-ссылки

### Шаг 5: Проверка

```bash
# Посмотри итоговые изменения
git diff
```

## Workflow: Обновление по ветке

**Вход:** `git diff main...{branch}`

### Шаг 1: Масштаб изменений

```bash
# Посмотреть список изменений
git log main...{branch} --oneline

# Посмотреть затронутые модули
git diff main...{branch} --stat
```

### Шаг 2: Параллельное исследование

Для каждого изменённого модуля запусти `Explore`-агента параллельно:

```
→ Explore: http-client-spring-boot-starter/src/main/java
→ Explore: logger-spring-boot-starter/src/main/java
→ Explore: vych-spring-toolkit-tests/src/main/java
```

### Шаг 3: Сравнение и обновление

Для каждого модуля:
1. Сравни `docs/modules/{module}.md` с фактической структурой
2. Сравни `README.md` модуля с текущим API и конфигурацией
3. Сравни `docs/packages/` с фактическими пакетами

### Шаг 4: Архитектура

Проверь `docs/architecture.md`:
- Актуальны ли зависимости между модулями?
- Актуальны ли паттерны проектирования?
- Актуальны ли ключевые решения?

### Шаг 5: Навигация

Проверь `docs/README.md`:
- Все ли ссылки работают?
- Нет ли ссылок на несуществующие файлы?
- Актуален ли обзор проекта?

## Workflow: Обновление модуля

**Вход:** "обнови документацию для модуля {module}"

### Шаг 1: Определение модуля

См. `docs/architecture.md` для определения пути модуля.

### Шаг 2: Исследование модуля

Запусти `Explore`-агента:

```
Исследуй модуль {module-path}/src/main/java.
Мне нужно обновить полную документацию модуля.
Собери:
1. Список всех пакетов
2. Для каждого пакета: публичные классы, методы, зависимости
3. Spring Boot автоконфигурация (@AutoConfiguration, @Bean)
4. Зависимости от других модулей (см. pom.xml)
5. Примеры использования из тестов
```

### Шаг 3: Обновление docs/modules/{module}.md

Сравни с текущим файлом:
- Список пакетов актуален?
- Зависимости актуальны?
- Публичный API описан полностью?
- Примеры использования актуальны?

### Шаг 4: Обновление README.md модуля

Проверь:
- Примеры использования (код актуален?)
- Конфигурация (свойства совпадают с кодом?)
- Публичный API (все публичные классы описаны?)
- Зависимости (версии, другие модули)

### Шаг 5: Обновление docs/packages/{package}.md

Для каждого пакета модуля:
- Список классов актуален?
- Назначение классов актуально?
- Ключевые методы актуальны?
- Зависимости между классами актуальны?

## Workflow: Полное обновление

**Вход:** "обнови документацию в проекте"

### Шаг 1: Исследование всех модулей

Запусти `Explore`-агентов **параллельно** для всех модулей:

```
→ Explore: logger-spring-boot-starter/src/main/java
→ Explore: http-client-spring-boot-starter/src/main/java
→ Explore: vych-spring-toolkit-tests/src/main/java
```

### Шаг 2: Проверка структуры docs/

```bash
# Посмотри структуру docs
find docs/ -type f -name "*.md" | sort

# Посмотри структуру packages
find docs/packages/ -type f -name "*.md" | sort
```

Сравни с фактической структурой кода:
- Нет ли пакетов без документации?
- Нет ли документации для удалённых пакетов?

### Шаг 3: Обновление по приоритету

1. `docs/architecture.md` — база для всей документации
2. `docs/modules/*.md` — модули
3. `docs/packages/*/README.md` — пакеты
4. `docs/README.md` — навигация
5. `README.md` в модулях — пользовательская документация
6. `docs/testing/*.md` — тестирование

### Шаг 4: Финальная проверка

- Все `last_updated` обновлены?
- Все кросс-ссылки актуальны?
- Нет файлов > 200 строк?
- Нет приватных сущностей в документации?
