# Spec Edit

Создание и обновление спецификаций в соответствии с гайдлайнами проекта.

## ⚠️ ВАЖНО: Уточняющие вопросы

**ОБЯЗАТЕЛЬНО** задавай уточняющие вопросы перед созданием или изменением спецификации.
Не додумывай требования — используй `NEEDS_CLARIFICATION` если поведение неизвестно.

## Правила проекта

**ОБЯЗАТЕЛЬНО** следуй гайдлайнам:
- [`docs/guidelines/specifications-guidelines.md`](docs/guidelines/specifications-guidelines.md) — структура, ID, правила написания
- [`docs/guidelines/implementation-guideline.md`](docs/guidelines/implementation-guideline.md) — связь spec ↔ реализация
- [`docs/guidelines/agent-documentation-guidelines.md`](docs/guidelines/agent-documentation-guidelines.md) — структура docs/, фронтматтер

## Сценарии

### 1. Создание новой спецификации

```
создай спецификацию для {описание функциональности}
```

1. Определи домен и имя файла
2. Задай уточняющие вопросы (см. ниже)
3. Напиши spec по структуре
4. Проверь качество (чек-лист)
5. Предоставь пользователю на утверждение

### 2. Обновление существующей спецификации

```
обнови спецификацию {spec-name}
```

1. Прочитай текущую spec
2. Определи что изменилось
3. Задай уточняющие вопросы по изменениям
4. Обнови spec
5. Проверь на противоречия с другими specs
6. Предоставь пользователю на утверждение

## Уточняющие вопросы

### Для новой спецификации

Задай вопросы по каждому применимому разделу:

**Purpose (цель):**
- Что именно должна делать эта функциональность?
- Зачем она нужна? Какую бизнес-проблему решает?

**Preconditions (предусловия):**
- Какие условия должны быть выполнены перед использованием?
- Какие модули/компоненты должны быть доступны?
- Нужна ли авторизация/аутентификация?

**Inputs (входы):**
- Какие данные принимаются?
- Какие типы, форматы, ограничения?
- Какие данные обязательные, какие опциональные?

**Behavior (поведение):**
- Что происходит при успешном выполнении?
- Что происходит при каждом сценарии использования?
- Какой порядок действий?
- Как обрабатываются edge cases?

**Business rules (правила):**
- Какие ограничения существуют?
- Какие правила валидации?
- Какие зависимости от других систем?

**Errors (ошибки):**
- Какие ошибки возможны?
- Как должны обрабатываться?
- Какие исключения бросаются?

**Acceptance criteria (критерии):**
- Как проверить, что функциональность работает?
- Какие конкретные проверяемые критерии?

**Examples (примеры):**
- Есть ли примеры использования?
- Нужны ли примеры для устранения неоднозначности?

### Для обновления спецификации

Задай вопросы по каждому изменению:

1. **Что изменилось?** — опиши конкретные изменения
2. **Почему изменилось?** — контекст изменения (баг, новое требование, рефакторинг)
3. **Как влияет на текущее поведение?** — текущее vs требуемое
4. **Есть ли противоречия с другими spec?** — проверь связанные спецификации
5. **Нужно ли обновить связанные specs?** — зависимости от других спецификаций

## Workflow

### Шаг 1: Определение scope

1. Определи домен (подкаталог в `specs/`)
2. Определи имя файла → ID спецификации
3. Определи связанные спецификации

### Шаг 2: Уточнение требований

**ЗАДАВАЙ ВОПРОСЫ** по каждому неясному пункту.
Не предполагай — если не уверен, используй `NEEDS_CLARIFICATION`.

### Шаг 3: Написание спецификации

Используй структуру из specs-guidelines:

```markdown
# {ID}-spec — {Название}

## Purpose
{что и зачем}

## Preconditions
{условия}

## Inputs
{входные данные}

## Behavior
{поведение}

## Business rules
{правила}

## Errors
{ошибки}

## Acceptance criteria
{критерии}

## Examples
{примеры, если нужно}
```

**Правила написания:**
- Описывай **поведение**, а не реализацию
- Используй однозначные формулировки: `должен`, `не должен`, `может`
- Не используй: `обычно`, `как правило`, `по возможности`
- Каждый requirement должен быть проверяемым
- Если поведение неизвестно — `NEEDS_CLARIFICATION`

### Шаг 4: Проверка качества

**Чек-лист перед предоставлением:**
- [ ] Требование однозначно?
- [ ] Понятно, что система должна делать?
- [ ] Описаны важные ограничения и исключения?
- [ ] Поведение можно проверить тестами?
- [ ] Нет деталей реализации без необходимости?
- [ ] Нет предположений, выданных за требования?
- [ ] Нет противоречий с другими спецификациями?
- [ ] ID сформирован правильно?
- [ ] Секции необязательные пропущены, если неприменимы?

### Шаг 5: Предоставление пользователю

Предоставь:
1. **Готовую спецификацию** — полный текст
2. **Список уточняющих вопросов** — что было уточнено, что осталось NEEDS_CLARIFICATION
3. **Список допущений** — если что-то было додумано (с пометкой)
4. **Связанные спецификации** — что нужно проверить/обновить

**Не вноси правки самостоятельно** — предоставь на утверждение.

## Формат отчёта пользователю

```
## Спецификация: {spec-id}

### Статус
- Новый файл: `specs/{domain}/{file}.md`
- ID: `{spec-id}`
- Секций: {N}

### Уточняющие вопросы
- Уточнено: {что уточнил пользователь}
- NEEDS_CLARIFICATION: {что осталось неясным}
- Допущения: {что было додумано, с пометкой "ДОПУЩЕНИЕ"}

### Связанные спецификации
- `specs/{domain}/{related}.md` — {как связано}

### Чек-лист качества
- [x] Требование однозначно
- [x] Поведение можно проверить тестами
- [x] Нет противоречий с другими specs
- ...

### Готовая спецификация
{полный текст spec}
```

## Примеры

### Хорошая спецификация

```markdown
# http-client-spec — HTTP Client Core

## Purpose
Типизированный HTTP-клиент для выполнения GET и POST запросов...

## Behavior
### Выполнение GET запроса
1. Все `RequestInterceptor` выполняются последовательно
2. Cookies для хоста запроса добавляются как `Cookie` header
3. Формируется `HttpRequest` с методом `GET`
4. Запрос отправляется через Java 11 `HttpClient.send()`
...

## Acceptance criteria
- [ ] `execute()` с `GET` запросом возвращает `Response` с правильным status code
- [ ] `execute()` с `POST` запросом отправляет сериализованное тело
```

### Плохая спецификация

```markdown
# Bad spec

## Описание
Клиент делает запросы к API.

## Поведение
Обычно работает корректно, если сервер доступен.

## Критерии
- Клиент работает хорошо
- Ошибки обрабатываются правильно
```
