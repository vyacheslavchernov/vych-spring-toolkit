# Project Coding Standards Checker

Проверяет соответствие Java-кода конвенциям проекта `vych-spring-toolkit`.

## Когда использовать

- Пользователь просит проверить код на соответствие правилам проекта
- Проверка конкретного модуля, файла, diff или всех изменений в ветке
- Pre-commit проверка перед отправкой изменений

## Входные данные

Определи масштаб проверки:
- **Весь проект** — сканировать все `**/*.java`
- **Модуль** — `http-client-spring-boot-starter/src/**`, `logger-spring-boot-starter/src/**`, `vych-spring-toolkit-tests/src/**`
- **Файл** — конкретный путь к `.java` файлу
- **Diff/изменения в ветке** — `git diff` или `git diff --staged`
- **Пакет** — конкретный Java-пакет (напр. `ru.vych.http.impl.entities`)

## Стратегия работы с большими объёмами

**Главное правило:** не проверяй большие объёмы кода в одном контексте. Разбивай на функциональные группы (пакеты) и используй суб-агентов для параллельной проверки.

### 1. Весь проект

**Шаг 1:** Определи модули и пакеты для проверки.
Найди все Java-пакеты:

```bash
# Найти все пакеты и количество файлов в каждом
find . -path '*/src/*/java' -type d | while read dir; do
  echo "=== $dir ==="
  find "$dir" -name '*.java' -exec dirname {} \; | sort -u | while read pkg; do
    count=$(find "$pkg" -name '*.java' | wc -l)
    echo "  $(basename "$pkg") ($count файлов)"
  done
done
```

Или используй `glob` с паттерном `**/src/*/java/**/*.java`.

**Шаг 2:** Запусти суб-агентов параллельно:

**Правила разбиения:**
- Пакеты ≤ 5 файлов → объединяй в одного агента (по 2-3 пакета)
- Пакеты > 5 файлов → отдельный агент
- Максимум 4-6 агентов параллельно на весь проект
- Разделяй main и test — запускай отдельно

**Примерная схема для текущего проекта:**
```
Агент 1: http-client/src/main → маленькие пакеты (config, common, interceptors, storage)
Агент 2: http-client/src/main → крупные пакеты (impl.entities, impl.exceptions, impl)
Агент 3: http-client/src/test → все test-пакеты
Агент 4: logger/src/main → все main-пакеты
Агент 5: logger/src/test → все test-пакеты
Агент 6: vych-tests/src/main → controllers + остальные
Агент 7: vych-tests/src/test → http/* (default package)
```

**Шаг 3:** Для каждого суб-агента передай:
- Точный путь к директории пакета (абсолютный или от корня проекта)
- Полный список проверяемых правил из `references/rules.md`
- Инструкцию вернуть **только** нарушения в стандартизированном формате (см. "Формат ответа суб-агента")
- Указать модуль и источник (main/test)

**Шаг 4:** Собери результаты от всех агентов, объедини нарушения, устрани дубли (если один файл попал в два агента), сформируй итоговый отчёт.

### 2. Один модуль (20-36 файлов)

**Шаг 1:** Разбей модуль на пакеты.

**Шаг 2:** Запусти суб-агентов:
- Пакеты ≤ 5 файлов — объединяй в одного агента
- Пакеты > 5 файлов — отдельный агент (или разбей на подгруппы)
- Максимум 2-3 агента параллельно на модуль

**Пример для http-client-spring-boot-starter (36 файлов):**
```
Агент 1: http-client/src/main → ru.vych.http.config + ru.vych.http.impl.common + ru.vych.http.impl.interceptors + ru.vych.http.impl.storage
Агент 2: http-client/src/main → ru.vych.http.impl + ru.vych.http.impl.entities + ru.vych.http.impl.exceptions
Агент 3: http-client/src/test → все test-пакеты
```

### 3. Один пакет (1-13 файлов)

Проверяй в своём контексте без суб-агентов. Читай все файлы пакета и проверяй каждое нарушение.

### 4. Один файл

Проверяй в своём контексте.

### 5. Diff / изменения в ветке

Не используй суб-агентов. Читай изменённые участки и проверяй только их.

## Процесс проверки

### 1. Для diff/staged изменений

```bash
# Все изменения в ветке
git diff HEAD -- '*.java'

# Или staged изменения
git diff --staged -- '*.java'
```

Изменённые файлы — источники для проверки. Для каждого изменённого участка проверяем правила ниже.

### 2. Для файлов/модулей/проекта

Найти все `.java` файлы в целевом диапазоне и проверить каждое нарушение.

### 3. Фиксация нарушений

Для каждого нарушения записывай:
- **Файл** — относительный путь
- **Строка** — номер строки (если применимо)
- **Правило** — название из `references/rules.md`
- **Описание** — что именно нарушено
- **Рекомендация** — как исправить (конкретный пример)

## Проверяемые правила

Смотри `references/rules.md` — полный список правил с примерами корректного/некорректного кода.

**Ключевые категории:**
1. **Naming** — пакеты, классы, методы, переменные, константы
2. **Структура класса** — порядок элементов, импорты
3. **Декомпозиция файлов** — приоритет декомпозиции при разрастании, лимит 1000 строк
4. **Вложенные классы** — запрет, исключения для паттернов (Builder)
5. **Lombok** — какие аннотации где использовать
6. **Builder Pattern** — кастомный inner class, валидация в `build()`
7. **Spring Boot** — `@AutoConfiguration`, constructor injection
8. **Исключения** — checked, naming, конструкторы, централизация сообщений
9. **Логирование** — только `LogService` или `System.out/err` для аппендеров
10. **Форматирование** — K&R, switch arrow, pattern matching, `List.of()`/`Map.of()`
11. **JavaDoc** — обязателен для публичных классов/методов/полей
12. **Тесты** — `@DisplayName`, `@SneakyThrows`, AssertJ `.describedAs()`, naming

## Статические импорты

Особое внимание — статические импорты вместо прямого обращения к `SomeClass.CONSTANT` или `SomeClass.method()`.

## Формат ответа суб-агента

Когда запускаешь суб-агента, укажи ему вернуть нарушения в формате:

```
## Нарушения в [пакет/модуль]

### 1. [Правило] Название правила
- **Файл:** `path/to/File.java`
- **Строка:** 42
- **Описание:** Что нарушено
- **Код:** (контекст 3-5 строк)
- **Рекомендация:** Как исправить

(если нарушений нет)
## Нарушений не найдено
```

Агент должен вернуть **только** нарушения, без лишних объяснений.

## Результат

Верни **детальный список нарушений** в формате:

```
## Нарушения (N шт.)

### 1. [Правило] Название правила
- **Файл:** `path/to/File.java`
- **Строка:** 42
- **Описание:** Что нарушено
- **Код:** (контекст 3-5 строк)
- **Рекомендация:** Как исправить
```

В конце — **Summary**:

```
Итого: N нарушений
- Критических: M (блокируют корректную работу)
- Стилевых: K (нарушают конвенции)
По категориям:
- Naming: X
- Lombok: Y
- JavaDoc: Z
...
```

## Важные ограничения

- **НЕ запускай checkstyle** (`mvn checkstyle:check`) — это отдельная проверка
- **НЕ предлагай править `checkstyle.xml`** — код должен соответствовать стандарту
- Проверяй только то, что указано в `references/rules.md`
- Если нарушение не подтверждено чтением кода — не сообщай о нём
- При использовании суб-агентов — не дублируй файлы между агентами
- Если суб-агент не нашёл нарушений, но ты видишь их при ручной проверке — сообщи свои нарушения отдельно
