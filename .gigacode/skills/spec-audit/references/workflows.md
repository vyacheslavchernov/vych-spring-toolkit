# Workflows — Spec Audit

Детальные пошаговые сценарии для аудита спецификаций.

## Промпты для Explore-агентов

### Исследование кода модуля

```
Исследуй модуль {module-path}/src/main/java.
Мне нужно проверить соответствие кода спецификации.
Собери:
1. Все публичные классы/интерфейсы/enum/record
2. Для каждого: публичные методы с сигнатурами
3. Иерархию исключений
4. Spring Bean'ы и автоконфигурацию
5. Публичный API (только то, что видно потребителю)
```

### Исследование тестов

```
Исследуй модуль {module-path}/src/test/java.
Мне нужно проверить покрытие тестами.
Собери:
1. Все тестовые классы и их названия
2. Какие сценарии покрывает каждый тест
3. Какие исключения проверяются
4. Есть ли параметризованные тесты для граничных случаев
```

### Исследование документации

```
Исследуй {doc-path}.
Мне нужно проверить актуальность документации.
Собери:
1. Описанный публичный API
2. Примеры использования
3. Конфигурация (свойства, параметры)
4. Зависимости и связанные компоненты
```

## Детальный workflow: Код ↔ Спецификация

### Шаг 1: Извлечение элементов spec

Для каждого раздела spec извлеки:

**Inputs → Публичный API:**
- Интерфейсы и их методы (имя, параметры, возвращаемый тип)
- Классы и их builder-методы
- Enum'ы и их значения
- Record'ы и их поля

**Behavior → Поведение:**
- Пошаговые сценарии (нумерованные списки)
- Условия выполнения
- Порядок действий

**Business rules → Правила:**
- Ограничения (что должно/не должно быть)
- Гарантии (что гарантируется)
- Константы и значения по умолчанию

**Errors → Исключения:**
- Ситуации, которые вызывают исключения
- Типы исключений
- Поведение при ошибках

**Acceptance criteria → Критерии:**
- Чек-лист проверяемых требований

### Шаг 2: Проверка каждого элемента

Для **публичного API**:
1. Найди класс/метод в коде
2. Проверь сигнатуру (имя, параметры, тип возврата)
3. Проверь наличие в интерфейсе и реализации
4. Отметь: ✅ соответствует / ❌ расхождение / ❓ не найдено

Для **поведения**:
1. Найди метод в коде
2. Сравни пошаговый алгоритм из spec с реализацией
3. Проверь порядок действий, условия, побочные эффекты
4. Отметь: ✅ соответствует / ❌ расхождение / ❓ не найдено

Для **бизнес-правил**:
1. Найди проверку правила в коде
2. Проверь, что правило реализовано
3. Отметь: ✅ реализовано / ❌ не реализовано / ❓ не найдено

Для **исключений**:
1. Найди бросание исключения в коде
2. Проверь тип исключения
3. Проверь условие бросания
4. Отметь: ✅ соответствует / ❌ расхождение / ❓ не найдено

### Шаг 3: Фиксация расхождений

Для каждого расхождения укажи:
- Элемент spec (секция, пункт)
- Что написано в spec
- Что есть в коде
- Тип расхождения (missing, wrong, extra)

## Детальный workflow: Тесты ↔ Спецификация

### Шаг 1: Mapping acceptance criteria → тесты

Для каждого acceptance criterion:
1. Ищи тест по ключевым словам из criterion
2. Проверяй, что тест проверяет именно это требование
3. Отметь: ✅ покрыт / ❌ не покрыт / ❓ частичное покрытие

### Шаг 2: Проверка покрытия поведения

Для каждого сценария в `Behavior`:
1. Найди тест, который его проверяет
2. Проверь, что тест воспроизводит все шаги
3. Отметь: ✅ покрыт / ❌ не покрыт

### Шаг 3: Проверка покрытия ошибок

Для каждого entry в `Errors`:
1. Найди тест, проверяющий это исключение
2. Проверь, что тест проверяет ситуацию и тип исключения
3. Отметь: ✅ покрыт / ❌ не покрыт

### Шаг 4: Проверка граничных случаев

Для каждого бизнес-правила:
1. Ищи тест на граничный случай (null, empty, boundary values)
2. Отметь: ✅ покрыт / ❌ не покрыт

## Детальный workflow: Документация ↔ Код + Тесты

### Шаг 1: Проверка docs/modules/*.md

1. Сравни список пакетов с фактическим
2. Сравни описание классов с кодом
3. Проверь примеры использования
4. Проверь конфигурацию

### Шаг 2: Проверка docs/packages/*/README.md

1. Сравни список классов с фактическим
2. Проверь сигнатуры методов
3. Проверь зависимости между классами

### Шаг 3: Проверка README.md модулей

1. Проверь примеры использования (код актуален?)
2. Проверь конфигурацию (свойства совпадают?)
3. Проверь публичный API

## Пример отчёта

```
# Spec Audit Report: logger-log-service-spec

## Summary
- Spec: specs/logger/log-service-spec.md
- Scope: module (logger-spring-boot-starter)
- Date: 2026-10-09

## 1. Код ↔ Спецификация

### Соответствует
- [x] Публичный API (debug/info/warn/error) — все методы реализованы в LogService
- [x] Создание LogEvent — LogEvent.create() с правильными параметрами
- [x] Фильтрация — фильтры применяются последовательно к каждому аппендеру
- [x] Обработка ошибок — LoggerException перехватывается, обработка продолжается

### Расхождения
- [ ] Метод log() — spec описывает перегрузку без message, в коде реализована только с message
- [ ] SERVICE_CODE — spec: "LoggerService", code: "ConsoleAppender"

## 2. Тесты ↔ Спецификация

### Покрыто
- [x] "LogService создаётся как Spring Bean" → LogServiceAutoConfigurationTests
- [x] "Методы debug/info/warn/error создают события" → LogServiceTests
- [x] "Фильтры применяются последовательно" → LogServiceFilterTests

### Не покрыто
- [ ] "UUID экземпляра генерируется один раз при создании" — нет теста
- [ ] NEEDS_CLARIFICATION: поведение при параллельном вызове

## 3. Документация ↔ Код + Тесты

### Соответствует
- [x] docs/modules/logger.md — список методов LogService актуален

### Расхождения
- [ ] docs/modules/logger.md — описан метод log() без message, но в коде его нет

## Итого
- Расхождений код↔spec: 2
- Непокрытых acceptance criteria: 1
- Расхождений docs↔code: 1
- Статус: WARN
```
