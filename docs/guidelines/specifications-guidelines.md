# Guideline по написанию спецификаций

## 1. Назначение

Спецификация описывает, **что система должна делать**, а не то, **как это реализовано**.

Спецификация должна быть однозначной, проверяемой и понятной без изучения исходного кода.

---

## 2. Расположение

Все спецификации хранятся в корне репозитория:

```text
specs/
├── README.md
├── {domain}/
│   ├── {feature}.md
│   └── ...
└── ...
```

Структура каталогов должна отражать предметную область, а не структуру Java-пакетов или классов.

Например:

```text
specs/
├── auth/
│   ├── login.md
│   └── registration.md
├── orders/
│   ├── creation.md
│   ├── cancellation.md
│   └── status-transitions.md
└── payments/
    └── refund.md
```

Не создавать отдельную спецификацию для каждого класса или метода.

### ID спецификации

ID спецификации формируется из пути файла относительно каталога `specs/`:

1. Берётся путь файла относительно `specs/` (без расширения `.md`)
2. Слэши `/` заменяются на дефисы `-`

Примеры:

| Файл | ID |
|---|---|
| `specs/http/send-request-spec.md` | `http-send-request-spec` |
| `specs/orders/creation-spec.md` | `orders-creation-spec` |
| `specs/auth/login-spec.md` | `auth-login-spec` |

### README.md

`README.md` в `specs/` и его подкаталогах используется для навигации и краткого описания содержащихся спецификаций.

Корневой `specs/README.md` должен содержать:

- назначение каталога `specs/`;
- описание используемой структуры;
- список доменов/разделов со ссылками на их `README.md`;
- краткое описание каждого раздела.

`README.md` внутри домена должен содержать:

- назначение домена;
- краткое описание его функциональности;
- список спецификаций со ссылками на них;
- при необходимости — зависимости или общие правила, относящиеся ко всему домену.

README не должен дублировать содержимое спецификаций.

---

## 3. Что должно быть в спецификации

Использовать следующую структуру:

```markdown
# {ID}-spec — {Название}

## Purpose

Что и зачем делает функциональность.

## Preconditions

Условия, необходимые для выполнения.

## Inputs

Входные данные и ограничения на них.

## Behavior

Подробное описание ожидаемого поведения.

## Business rules

Правила и ограничения.

## Errors

Ошибки и условия их возникновения.

## Acceptance criteria

Проверяемые критерии приемки.

## Examples

Примеры поведения, если они помогают устранить неоднозначность.
```

## ID спецификаций

ID формируется из пути файла относительно `specs/`:
1. Берётся путь без расширения `.md`
2. Слэши заменяются на дефисы

Пример: `specs/logger/file-appender-spec.md` → `logger-file-appender-spec`

Необязательные секции можно пропускать, если они неприменимы.

---

## 4. Описывать поведение, а не реализацию

Спецификация должна быть независима от конкретных классов, методов и фреймворков.

Плохо:

```text
OrderController вызывает OrderService,
который вызывает OrderRepository.save().
```

Хорошо:

```text
После успешного создания заказа
заказ должен быть сохранён и доступен для последующего получения.
```

Исключение — технические ограничения, которые сами являются требованием системы.

---

## 5. Формулировать требования однозначно

Использовать конкретные формулировки:

```text
должен
не должен
может
только если
всегда
никогда
```

Не использовать неопределённые формулировки:

```text
обычно
как правило
по возможности
желательно
примерно
```

Каждое требование должно позволять однозначно определить, выполнено оно или нет.

---

## 6. Не выдумывать требования

Если поведение неизвестно, его нельзя додумывать.

Использовать:

```text
NEEDS_CLARIFICATION
```

Например:

```text
NEEDS_CLARIFICATION:
Не определено, должен ли повторный запрос создавать
новую операцию или возвращать результат предыдущей.
```

Особенно важно соблюдать это при генерации спецификаций AI-агентом.

---

## 7. Разделять требования и текущее поведение

Для существующего проекта не считать текущее поведение автоматически правильным.

Если оно отличается от требуемого:

```text
Current behavior:
повторный запрос создаёт новую операцию.

Required behavior:
повторный запрос с тем же идентификатором
не должен создавать новую операцию.
```

Такое расхождение должно быть явно указано.

---

## 8. Acceptance criteria

Критерии должны быть конкретными и проверяемыми.

Хорошо:

```markdown
- [ ] Пользователь может создать заказ из непустой корзины.
- [ ] Нельзя создать заказ из пустой корзины.
- [ ] Нельзя создать заказ с недоступным товаром.
- [ ] После успешного создания корзина очищается.
- [ ] При ошибке корзина не изменяется.
```

Плохо:

```markdown
- [ ] Заказ создаётся корректно.
- [ ] Ошибки обрабатываются правильно.
```

---

## 9. Не дублировать документацию

`docs/` описывает устройство проекта.

`specs/` описывает требуемое поведение.

Не копировать архитектуру, описание классов и структуру пакетов в спецификации, если это не является частью требования.

---

## 10. Качество спецификации

Перед добавлением спецификации проверить:

- Требование однозначно?
- Понятно, что система должна делать?
- Описаны важные ограничения и исключения?
- Поведение можно проверить тестами?
- Нет деталей реализации без необходимости?
- Нет предположений, выданных за требования?
- Нет противоречий с другими спецификациями?

Если на какой-либо вопрос нельзя ответить однозначно — спецификацию необходимо уточнить до статуса готовой.
