# Agent Documentation Guidelines

## Назначение

Этот гайдлайн описывает правила создания и поддержки документации, оптимизированной для **использования другими AI-агентами**. Основная цель — минимизировать контекстное окно при сохранении всей необходимой информации через иерархическую структуру с кросс-ссылками.

---

## 1. Структура документации

### 1.1 Иерархический принцип (drill-down)

Документация строится по принципу от общего к частному:

```
docs/
├── README.md                          # Главная: обзор проекта, навигация
├── {architecture}.md                  # Архитектура, паттерны, зависимости
├── guidelines/
│   ├── commit-guidelines.md           # Конвенции оформления коммитов
│   ├── agent-documentation-guidelines.md  # Правила создания документации для AI
│   └── specifications-guidelines.md   # Правила написания спецификаций
├── modules/
│   ├── README.md                      # Обзор модулей (что есть, зачем)
│   ├── {module}.md                    # Модуль: назначение, ключевые классы
│   └── ...
├── packages/
│   ├── {module}/
│   │   ├── {package}.md               # Пакет: обзор
│   │   ├── {subpackage}.md            # Подпакет
│   │   └── ...
│   └── ...
└── testing/
    ├── overview.md                    # Фреймворки, конвенции тестирования
    ├── unit-tests.md                  # Юнит-тесты (покрытие, паттерны)
    └── integration-tests.md           # Интеграционные тесты, mock-сервер
```

**Правило:** один файл — одна логическая единица. Не более 200 строк. Если файл растёт — разбивай.

### 1.2 Кросс-ссылки

Каждый файл должен содержать ссылки на соседние:

- **Модуль** → ссылки на документацию пакетов внутри модуля
- **Пакет** → ссылки на файлы классов (через `packages/...`) и на модуль, которому принадлежит
- **Главная** → ссылки на все модули и разделы

```markdown
## Пакеты модуля
- [`config`](../packages/http/config.md) — автоконфигурация Spring
- [`impl`](../packages/http/impl.md) — реализации HTTP-клиента
- [`impl/entities`](../packages/http/impl/entities.md) — сущности Request/Response
```

## 2. Обязательные метаданные

### 2.1 Дата последнего обновления

**Каждый** документ должен начинаться с YAML-фронтматтера:

```yaml
---
last_updated: 2026-10-08
scope: module | package | testing | architecture
---
```

- `last_updated` — дата в формате `YYYY-MM-DD`. Обновляется при любом изменении документа или связанного кода.
- `scope` — тип документа: `module`, `package`, `testing`, `architecture`.

### 2.2 Структура заголовка документа

После фронтматтера — краткое описание (1-2 предложения) о том, что здесь находится. Это помогает агенту быстро понять релевантность без чтения всего файла.

## 3. Содержание документов

### 3.1 Документ модуля (`modules/*.md`)

**Что включать:**
- Назначение модуля (1-2 предложения) — **зачем он нужен**
- Публичные возможности (что потребителю видно)
- Список пакетов с кратким описанием каждого (1 предложение)
- Зависимости модуля (compile/runtime/test)
- Ссылки на документацию пакетов (`packages/...`)
- Обобщённая информация о тестах: какие сценарии покрыты, в каких файлах

**Что НЕ включать:**
- Детали каждого класса (это в `packages/`)
- Полные листинги кода
- Описание приватных методов

### 3.2 Документ пакета (`packages/*/README.md`)

**Что включать:**
- Полный список публичных классов/интерфейсов/enum/record
- Для каждого: назначение (1 предложение), ключевые методы, зависимости от других классов пакета
- Диаграмма связей (ASCII-диаграмма, если уместно)
- Ссылки на модуль и соседние пакеты

**Что НЕ включать:**
- Приватные классы и методы
- Полные сигнатуры методов (агент прочитает исходник)
- Описание Lombok-аннотаций (если нет специфического поведения)

### 3.3 Документ тестов

**Что включать:**
- Обзор структуры тестовых пакетов
- Какие сценарии покрыты (обобщённо: "GET с кастомными хедерами", "POST с JSON body")
- Где искать конкретные тесты (пакеты, имена файлов)
- Описание mock-сервера (эндпоинты, конфигурация)
- Известные пробелы в покрытии

### 3.4 Главный `docs/README.md`

**Что включать:**
- Краткий обзор проекта
- Навигация по документации (ссылки на все разделы)
- Ссылку на `GIGACODE.md` (coding standards, build commands)

## 4. Использование суб-агентов

### 4.1 Обязательно используй суб-агентов

При создании или обновлении документации **всегда делегируй исследование кода суб-агентам**. Не пытайся читать файлы самостоятельно — это неэффективно.

### 4.2 Когда запускать суб-агентов

| Сценарий | Действие |
|---|---|
| Создание документа модуля | Запусти `Explore`-агента для исследования всех пакетов модуля |
| Создание документа пакета | Запусти `Explore`-агента для анализа публичных классов |
| Обновление документации | Запусти `Explore`-агента для поиска изменений в коде |
| Проверка полноты | Запусти `Explore`-агента для сравнения документов с фактической структурой |

### 4.3 Промпт для суб-агента

При делегировании задачи используй чёткий промпт:

```
Исследуй пакет {package-path} в модуле {module}.
Мне нужна документация для AI-агентов. Собери:
1. Список всех публичных классов/интерфейсов/enum
2. Назначение каждого (1 предложение)
3. Ключевые методы и их назначение
4. Зависимости от других классов пакета
5. Lombok-аннотации (только если влияют на поведение)
6. Особые паттерны или нюансы

Формат ответа: структурированный markdown-список.
```

### 4.4 Параллельный запуск

Запускай суб-агентов **параллельно** для разных пакетов/модулей:

```
→ Explore: http-client/config
→ Explore: http-client/impl
→ Explore: http-client/impl/entities
→ Explore: http-client/impl/common
```

## 5. Стиль написания

### 5.1 Язык

- Основной текст — **русский**
- Технические термины, названия API, классов, методов — как в коде (английский)
- Javadoc-комментарии в коде — не переводить, они и так на русском

### 5.2 Форматирование

- **Классы и интерфейсы**: `` `ClassName` ``
- **Методы**: `` `methodName()` ``
- **Пакеты**: `` `ru.vych.http.impl` ``
- **Ключевые понятия**: **жирный** для выделения
- **Код**: только если без него не понять (например, пример конфигурации)

### 5.3 Конкретика вместо общих фраз

| ❌ Плохо | ✅ Хорошо |
|---|---|
| "Класс для работы с HTTP" | "Обёртка над Java 11 `HttpClient`, поддерживает GET/POST с Jackson-десериализацией" |
| "Много методов" | "6 публичных методов: `get()`, `post()`, `buildRequest()`, `execute()`, `setInterceptor()`, `getCastedBody()`" |
| "Поддерживает кастомизацию" | "Интерфейс `RequestInterceptor` для модификации запроса, `ResponseInterceptor` для обработки ответа" |

## 6. Процесс создания документации

### 6.1 Пошаговый алгоритм

1. **Определи scope** — что нужно задокументировать (модуль, пакет, раздел)
2. **Запусти суб-агентов** для параллельного исследования кода
3. **Собери результаты** от суб-агентов
4. **Создай/обнови документ** по шаблону (фронтматтер + содержание)
5. **Добавь кросс-ссылки** на соседние документы
6. **Проверь полноту** — запусти `Explore`-агента для сравнения документов с фактической структурой

### 6.2 Чек-лист перед сохранением

- [ ] Фронтматтер с `last_updated` и `scope`
- [ ] Краткое описание в начале (1-2 предложения)
- [ ] Все публичные сущности описаны
- [ ] Кросс-ссылки на соседние документы добавлены
- [ ] Нет полных листингов кода
- [ ] Нет приватных методов и классов
- [ ] Язык: русский + технические термины на английском
- [ ] Файл ≤ 200 строк (если больше — разбей)

## 7. Примеры

### 7.1 Пример документа модуля

```yaml
---
last_updated: 2026-10-08
scope: module
---
```

# HTTP Client Starter

Spring Boot starter для HTTP-клиента с поддержкой GET/POST, интерсепторов, cookie и логирования.

## Назначение

Предоставляет типизированный HTTP-клиент с builder-паттерном, Jackson-десериализацией и UUID-трейсингом.

## Пакеты

- [`config`](../packages/http/config.md) — автоконфигурация Spring, `HttpClientBuilder`, `HttpClientConfig`
- [`impl`](../packages/http/impl.md) — основные реализации: `HttpClient`, `HttpClientImpl`, `HttpClientLogger`
- [`impl/common`](../packages/http/impl/common.md) — enum'ы (`HttpMethod`, `CookiesPolicies`), константы статуса и media-type
- [`impl/entities`](../packages/http/impl/entities.md) — сущности: `Request`, `Response`, `CookieEntry`, `Header`
- [`impl/exceptions`](../packages/http/impl/exceptions.md) — checked-исключения: `HttpClientException` + 4 сабкласса
- [`impl/interceptors`](../packages/http/impl/interceptors.md) — функциональные интерфейсы интерсепторов

## Зависимости

- **Compile**: `spring-boot-starter`, `logger-spring-boot-starter`, `lombok`, `jackson-databind`
- **Test**: `junit-jupiter`, `mockito-core`, `assertj-core`

## Тесты

Юнит-тесты (~28 классов) покрывают: создание клиента, GET/POST запросы, десериализацию, интерсепторы, обработку статусов.
Интеграционные тесты в `vych-spring-toolkit-tests` проверяют работу с mock-сервером (Jersey/Grizzly на :9090).

### 7.2 Пример документа пакета

```yaml
---
last_updated: 2026-10-08
scope: package
---
```

# ru.vych.http.impl

Основные реализации HTTP-клиента.

## Публичные классы

### `HttpClient` (interface)
Контракт HTTP-клиента. Методы: `get(Request, Class<T>)`, `post(Request, Class<T>)`.

### `HttpClientImpl`
Реализация поверх Java 11 `HttpClient`. Поддерживает GET/POST, кастомные хедеры, cookie-политики, редиректы. UUID-трейсинг для каждого запроса.

### `HttpClientLogger`
Обёртка над `LogService` для логирования запросов и ответов. Включается флагом `httpClient.log-requests`.

## Зависимости

- `HttpClientImpl` → `HttpClientLogger`, `Request.Builder`, `Response`
- `HttpClientLogger` → `LogService` (из logger-модуля)

## Связанные пакеты

- [`config`](./config.md) — `HttpClientBuilder` создаёт экземпляры `HttpClientImpl`
- [`impl/entities`](./entities.md) — использует `Request` и `Response`

## 8. Обновление документации

### 8.1 Триггеры для обновления

- Добавление нового публичного класса/метода
- Изменение публичного API (сигнатуры, поведение)
- Добавление нового пакета
- Изменение архитектуры или паттернов
- Файл документации давно не обновлялся (больше 30 дней)

### 8.2 Процесс

1. Запусти `Explore`-агента для поиска изменений
2. Сравни результаты с текущей документацией
3. Обнови соответствующие файлы
4. Обнови `last_updated` и кросс-ссылки

> **Примечание:** Обновление документации — отдельный процесс, не часть коммита с кодом.
